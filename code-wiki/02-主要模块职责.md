### 深链消费中枢（本模块最关键的职责）

`MainTabView` 对 `NotificationManager` 的 **5 个 `pending*` 字段**各挂一个 `onChange`，统一走「延迟调度」而非直接弹窗 [实测]：

| 通道 | 消费点 | 目的地 |
|---|---|---|
| 文章 | `consumePendingDeepLink` `:51`，`onChange` `:290` | `EnhancedNewsDetailView` sheet |
| 校长信箱 | `onChange` `:296` | 信件详情 sheet |
| 学校概况 | `onChange` `:307` | `SchoolProfileView` sheet |
| 党建专题 | `onChange` `:316` | `PartySubjectView` sheet |
| 机构动态 | `consumePendingOrgArticleDeepLink` `:85`，`sheet(item:)` `:413` | 机构文章详情 sheet（**2026-10-02 单状态化**：纯 item 驱动 + 消息中心来源等待 sheet 完全退场再 present + 550ms 错峰，修复冷启动白屏） |

**延迟调度算法**（`scheduleNotificationArticlePresentation` `:116-176`）：

1. 并行启动 `DataService.preloadArticleDetail` 预加载（秒开）；
2. 循环等待 `scenePhase == .active && !biometricSecurity.isLockEngaged`，每 100ms 一次、最多 30 次（≤3s）；
3. 超时 → `deepLinkOutcome = .failed(reason:)` 并保持待展示态；
4. 成功 → 再 `sleep(350ms)` 让出 runloop 周期 → 弹 sheet → `deepLinkOutcome = .presented(articleId)`。

**三重补发**（防漏接）：`.onAppear` 补消费一次（`:284-289`，覆盖冷启动 `didReceive` 早于视图出现）；`scenePhase == .active` 补发（`:328-335`）；`biometricSecurity.state == .unlocked` 补发（`:336-341`）。

> 🔴 **红线**：绝不在系统通知回调的同步链中弹 sheet，否则触发 `Call must be made on main thread` 崩溃（见 `:113-116` 与 `:290-295` 的源码注释）。

### `doFullSync` 流程（`:243`）

1. `syncLog = []` 并记录开始时间；
2. **串行拉取三个基础接口**：`home2` / `head` / `foot`，每个独立 `do/catch`（`home2` 失败写 `lastError`，其余写 `syncErrors`）；
3. **三者全失败 → `loadCache()` 回退，`dataSource = "缓存"`，直接 return**（`:270-273`）；
4. Banner（`:278-282`）；荣誉栏目 ≤50 条（`:285-294`）；
5. 5 个新闻栏目分页（重要新闻 / 更新 / 党建 / 通知 / 招生）；
6. 视频 `TaskGroup` 并行提取；
7. 院系数据与预置数据合并 → `OrganizationManager.updateSiteKeys()`；
8. `saveCache()` 写 21 个 JSON 缓存键（`:1012`）；
9. 后台加载招生网数据与专业数据。

### 三项关键约束

| 约束 | 位置 | 说明 |
|---|---|---|
| 冷却 | `:177` `syncCooldown = 10` | 10s 内重复调用直接跳过 |
| 缓存模式联动 | `:188-195` | 缓存模式下 600s 内成功过则跳过远程同步 |
| 取消语义 | `:102`（NetworkService 侧） | `.cancelled` 不算失败，不重试、不记 ERROR |

### 为何用「完成回调版」delegate 而非 async 版（`:950-992`）

源码注释给出的完整因果链（**注意：此为注释声明，未在本轮独立复现**）：

1. async 版 `userNotificationCenter(_:didReceive:) async` 由系统在**任意后台协作队列**派发；
2. UIKit 的通知响应处理（快照 / 状态恢复 `CATransaction` 提交）会**随回调在同一后台队列**执行；
3. 触发 `Call must be made on main thread` 断言崩溃——注释指认为**「点击通知闪退根因」**；
4. 完成回调版由系统保证在**主线程**派发，配合内部 `Task { @MainActor }` 形成双保险。

实现细节：方法标 `nonisolated`（`:976`，因类本身 `@MainActor`）；`completionHandler()` **在处理任何业务逻辑之前立即回执**（`:984`）；随后 `Task { @MainActor in handleNotificationTap(...) }`（`:985-991`）。`willPresent`（`:959-973`）同理：先回执，日志埋点放异步主线程（「绝不阻塞系统回调」）。

### `handleNotificationTap` 分发顺序（`:998-1107`）

**顺序即优先级**：

1. `schoolProfileDeepLink == true` → `markRead(kind: .schoolProfile)` → `pendingSchoolProfileDeepLink = true`；
2. `partySubjectDeepLink == true` → `markRead(kind: .partySubject)` → `pendingPartySubjectDeepLink = true`；
3. `orgArticleId` 非空 → `markRead(id: "org-{id}")` → 构造 `PendingOrgArticleDeepLink`（含归因四元组）；
4. `mailboxId` 非空 → `markRead(id: "mailbox-{id}")` → `pendingMailboxDeepLink`；
5. 兜底按文章处理：空 `articleId` **只记 warning 不跳转**（`:1088-1093`）；
6. 收藏归因：`isBookmarkUpdate == true` → `markRead(kind: .bookmarkUpdate, articleId:)`，否则 `markRead(id: "news-{articleId}")`；
7. `pendingDeepLink = PendingArticleDeepLink(...)`。

`PendingArticleDeepLink` / `PendingOrgArticleDeepLink`（`:36-75`）**都含 `let id = UUID()`**——每次点击生成新实例，保证 `onChange` 每次都触发（绕开「相同值不触发 `onChange`」）。
